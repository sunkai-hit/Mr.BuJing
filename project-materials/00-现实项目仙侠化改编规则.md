# 现实项目仙侠化：改编规范（V0.2）
> 修订：2026-10-30。本仓库为公开仓库。以下仅为**经虚构化处理的软件需求原型**，不代表任何真实项目发生过所述事故或争议。

## 创作公式
**现实业务困境 → 修仙世界里的诉求和利益 → 软件需求澄清 → 团队实现与测试 → 真实验收 → 系统奖励/人物代价**。

同一问题至少经过六问：谁提需求？真正使用者是谁？利益冲突在哪里？可交付软件功能是什么？专业角色怎样实现和验证？结局留给谁何种影响？

## 边界
1. 取通用机制而不取真实客户故事：不得写入真实企业、真实工作人员、非公开合同价格、源代码、账号、IP、部署拓扑、会议记录与商业机密；姓名、数据、事故、动机一律重新虚构或组合改写。
2. **不等于把软件需求说明书直接改称「仙术」**：需求必须有戏剧人物、有限资源、关键选择、代价与反转。技术黑话先让普通读者理解，再让行业读者会心一笑。
3. 顾不惊懂产品与管理，不是超一流架构师：沈听澜写核心阵法，苏小满负责测试，白知微部署运维，洛绯衣承担商务谈判；重要技术决策须经专业论证。
4. 「写PRD/开会/沟通/提建议/签合同」本身**不能领取软件需求完成奖励**；需实现具有独立使用价值的可验证软件功能，经授权验收且运行可信。基本每个真实软件研发需求能力值+1，不能拆单刷点。
5. 与客户对线要基于事实、约束与利益，达成双方认可的范围、责任和方案，生命值基础+1；赢吵架、侮辱客户、签完无法履约的合同不给奖励。
6. 真实项目的风险只作灵感，小说里具体阴谋、破坏、丑闻等均属于**原创虚构**，不影射现实人物。
7. 为了节奏可将多个真实需求凝缩成一个情节，也可将同一复杂需求拆为连续数章推进，但不得为了「刷系统能力值」重复验收同一价值。

## 单条故事素材入库模板
- **编号/拟定章节**：不可重复的素材ID；不必所有素材都用。
- **现实原型**：行业级通用业务，不含任何客户身份。
- **修仙化需求**：一个能交付的软件功能及验收场景。
- **冲突**：谁想要，谁反对，各自理由何在。
- **戏剧事件**：喜剧误会、危险意外、反转（明确虚构）。
- **人物成长**：主角与专业角色各作何选择。
- **系统结算**：能力值仅在软件能力验收通过时+1；对线共识另有生命值。
- **后果**：后续维护、声誉、责任、流程债或技术债。

## 项目故事分级
- **S级主线单元**：8—15章；与人物命运和卷终事件直接相关。例：护山运营预警一期、跨宗御剑云平台。
- **A级情节单元**：3—7章；一个实际项目需求加利害冲突。例：冻结库存的紧急放行。
- **B级功能桥段**：1—2章；制造笑点或解决一小步困难。例：审批用古代官印做授权。
- **C级彩蛋**：一句话或半场戏；只作行业笑点，不为凑素材强行加支线。

## 从真实工作到小说的流程
抽象需求/冲突 → 批量写故事卡 → 为每卷选出最有戏的少量项目 → 排章节和人物弧线 → 写场景 → 核对时间、成本、功能验收与系统数值 → 试写 → 再改。**现实项目是素材池，不是必须完整复刻的章节顺序。**

## 暂存与新增
第一批选三个熟悉的深水区——WMS、制造业ERP、无人系统云平台，各十条故事种子。其余IP代理、灵讯准入、丹医AI是后续卷主要补充源，先完成框架映射，不凭空认定真实事故。
