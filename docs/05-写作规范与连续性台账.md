# 写作规范、连续性与版本台账（V0.2）
> 用途：支持后续「编辑方案→试写→正式稿」协作。已进入正文创作阶段；第一卷第1章为正式稿，其他章节尚未正式完成。

## 1. 正文写作原则
1. **故事优先于黑话**：用冲突表现产品方法，不罗列现代产品经理培训材料；术语首次出现须有情境解释。
2. **一章一个主要动作**：每章有明确目标、阻力、行动、后果和尾钩；可以含副线，但不让主线迷失。
3. **笑点要服务角色**：合欢宗女修是独立专业人士，不是男性主角的布景；不靠低俗露骨描写推动剧情。
4. **爽点必须付代价**：项目成功要归因于团队、资源、风险控制和真实验收，系统奖励不免除现实后果。
5. **专业底线**：产品经理不装懂术法；开发决定与测试否决由相关专业角色参与。客户不是一律敌人。
6. **节奏渐进**：前80章高频荒诞喜剧，80—160章展开多宗格局，161章后严肃主线更重但保留诙谐对话。
7. **叙事视角**：第三人称限知，以顾不惊为主要焦点；切换视角须有场景标志，避免随时读心。

- 前10章用 ERP型报销审批/查重/权限/日志/测试/运维贯穿；中后30章用设备接入、运营监测、异常、合同责任、日志取证与试运行构造统一故事，不再写成随机仙术需求合集。
- 章节里应至少标记一次「需求是谁的、做成什么功能、谁实现、如何验收」。写文档或开会不加能力值；必须有独立软件验收才加能力基础+1。对线生命值必须有双方认可的共识记录。

- 后续每次项目素材入库添加素材ID、预定卷章、戏剧功能、验收标准、系统结算、人物选择、是否已用于正文；故事写法可以取舍，不要求复刻真实产品全流程。
